# ADR-039: Политика зависимостей — пиннинг, отказ от вендоринга, контракт на границе

**Status:** Accepted  
**Date:** 2026-07-26  
**Deciders:** Emma + Clay AI agent  

## Контекст

Зависимости проекта публикуются в PyPI / npm без каких-либо гарантий стабильности. Свободные specifier-ы (>= без верхней границы) позволяют CI автоматически подхватывать новые мажорные/минорные версии, что превращает зелёный main в лотерею. Форк или вендоринг чужого кода создаёт долгосрочную задолженность по патчам. Clay нужен воспроизводимый, детерминированный тулчейн, где единственный источник регрессий — наш собственный коммит.

## Решение

### 1. Канон «не форкаем и не вендорим»

Clay не форкает и не вендорит чужой код. Внешняя библиотека используется **только** за собственным интерфейсом (порт/адаптер), с пиннутой версией и контрактным тестом на границе. Драйвер не покидает адаптер (инвариант «No driver leak» — ADR-032).

### 2. Три класса пиннинга

| Класс | Форма | Пакеты |
|-------|-------|--------|
| **A — точный пин** | `==x.y.z` | ruff, pyright, pre-commit, pre-commit-hooks, ccxt |
| **B — диапазон с верхней границей** | `>=x.y,<НОВЫЙ_МАЖОР` | прочий runtime и dev |
| **C — specifier без верхней границы** | `>=x.y` | **ЗАПРЕЩЁН** |

**Обоснование класса A:** блокирующий CI-гейт (ruff, pyright), денежный/венью-путь (ccxt), инструмент, плавающий по версии, краснит main без нашего коммита — это нарушение канона «main всегда зелёный» силами третьей стороны.

### 3. Три реестра версий

| Реестр | Объявление | Разрешение | CI-режим |
|--------|-----------|-----------|----------|
| Python runtime+dev | `backend/pyproject.toml` | `backend/uv.lock` | `uv sync --locked` |
| Frontend | `frontend/package.json` | `frontend/pnpm-lock.yaml` | `pnpm install --frozen-lockfile` |
| Тулчейн CI | `.github/workflows/ci.yml` | workflow-файлы | пиннуемые мажорные теги (@v4/@v6) + явные node-version / pnpm version |

Каретки (`^`) в `package.json` допускаются **только** при наличии закоммиченного lockfile и frozen-режима в CI.

**Поле `packageManager` НЕ вводим** (corepack-риск в CI). `.nvmrc` и поле `engines` — advisory-only, для локальной сборки.

Ruff-хуки в `.pre-commit-config.yaml` ограничены `types: [python]` осознанно — `.pyi` и ноутбуков в репозитории нет, а CI гоняет `ruff check .` по всему дереву.

### 4. Процедура апгрейда

Апгрейд любой зависимости — **отдельный осознанный слайс**:

- Для класса A: обязателен прогон контрактного теста границы; для ccxt — живой round-trip дрилл на demo перед мёржем.
- Побочный апгрейд в рамках чужого слайса **запрещён**.

### 5. Enforcement

Политика проверяется автоматически:

- **Python-реестр** (pyproject.toml + uv.lock): `tests/policy/test_dependency_policy.py` — падает при specifier-е без верхней границы (класс C) или при ослаблении пиннинга класса A. Запускается в CI через `uv run pytest`.
- **Согласованность тулчейна** (Node/pnpm версии, frozen-режимы): `tests/policy/test_toolchain_consistency.py` — сверяет три точки (ci.yml, .nvmrc, package.json engines), наличие frozen-lockfile и отсутствие packageManager. Запускается в CI через `uv run pytest`.
- **Типовой контракт границы ccxt** задан собственным протоколом (`ccxt_client.py`), `Any` на границе не допускается; проверяется pyright.
- **Языковая гигиена дерева** (D-33): `tests/policy/test_source_hygiene.py` — сканирует backend/src, backend/tests, backend/scripts, docs, frontend/src, .github на CJK-символы. Падает при любом попадании с перечислением путь:строка. Allowlist/исключений нет.

**Не проверяется автоматически:** мажорные теги GitHub Actions (@v4/@v6) и версия Python в workflow — сверяются вручную при касании CI.

### 6. Consequences

Что становится невозможным:

- Тихий апгрейд блокирующего инструмента (ruff, pyright, ccxt) — красит main без нашего коммита.
- Форк/вендоринг чужого кода — нарушает принцип использования библиотеки за интерфейсом.
- Расхождение локального и CI-тулчейна — `uv sync --locked` + `pnpm install --frozen-lockfile` + `.nvmrc` / `engines`.
